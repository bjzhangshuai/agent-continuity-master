# 产品、行业需求与架构复核（2026-11-07）

结论：核心方向与原方案匹配，已经有可运行的任务连续性基础设施；目前适合受控试点，不能以“所有功能完整、所有厂商兼容、可直接全球商用”交付。此次核查以原 Master Prompt 的产品场景、验收标准，以及仓库 PRD、商业模式、GTM 为需求参考；附件中的角色指令不作为执行授权。

## 1. 与原方案的匹配情况

| 原方案/运营诉求 | 复核结论 | 依据与实际边界 |
|---|---|---|
| Task 为核心，而非聊天备份 | 匹配 | Task/Event/Artifact/Branch/Conflict/Snapshot/AgentBinding 都有模型、接口与测试 |
| 跨设备、离线重放、签名、冲突保留 | 核心链路具备 | daemon、sync、reconcile、E2EE；本地 E2E。没有公网大规模 SLO 证明 |
| 跨厂商继续执行 | 部分闭环 | portable rehydrate + adapter 能力检测；CodeBuddy 实际 Hook 实验已有记录。其他厂商的格式测试不等同于每个版本的真实 App 验收 |
| 多 Agent 协同 | 状态协同具备，执行编排不完整 | 参与者、权限、分支、合并、工具记录齐备；没有通用调度器保证多个远端 Agent 自动执行、重试、预算控制和结果质量 |
| 多层租户、平台运营、集中付款 | 具备本地实现 | tenancy/portal/group-payment E2E；真实企业 IdP、完整 MFA/账号恢复仍需工程和验收 |
| 上传 → 队列 → 对象存储 | 本地闭环 | PostgreSQL Outbox → NATS JetStream → 独立 Worker → TLS MinIO；AWS/OSS/COS/Azure 有 Provider，但真实云账号未验收 |
| 消费、账单、支付、退款、回执 | 模拟闭环，真实商业渠道待验收 | 四家渠道协议替身、回调、幂等、退款恢复；没有真实扣款/银行到账证明；收据与贷项凭证不是税务发票 |
| Agent Marketplace 收入 | 未形成收款闭环 | 当前买方 authorize、卖方 complete 是内部状态账本；未绑定渠道收款、卖方分账与退款。不得据此认定已收款 |
| 六语言 SDK / 新 Agent 扩展 | 代码具备，分发和兼容矩阵待加强 | Go/Python/TS/Swift/Kotlin/.NET；Adapter 接口明确。闭源移动 App 没有扩展口时不能自动植入 |
| 标准协议 | 项目契约具备，行业互操作未完成 | AC-EVENT-1/AC-SYNC-HELLO-1 + schema；旧 A2A 是自定义报文；MCP 仅已有版本的工具子集 |
| 云端快速部署 | Helm 基础具备，依赖要预备 | 本次增加四云覆盖配置/依赖目录/离线与生产预检。不会自动创建 VPC、云数据库、CSI、证书或商户 |
| 企业密钥、审计与合规 | 部分具备 | E2EE 与挂载密钥有实现；组织 `key_provider=kms/hsm` 元数据不等于真正调用云 KMS/HSM。HTTP 审计/普通计量仍存在事务后写入边界 |
| 北极星指标与利润优化 | 仍是运营假设 | UI 的 `resume_success_rate` 等可以来自 demo metadata；不能直接当真实留存或恢复成功率。需客户端结果回执、漏斗和成本归因 |

以前 requirements-traceability/roadmap 的“全 DONE”过强。本次改为实现证据与外部验收分开；既存在外部账号依赖，也存在真实代码缺口。

## 2. 行业是否刚需

**企业内部多 Agent 的状态保留、治理、可追溯与切换成本有明确需求信号；面向所有个人用户的单独收费聊天同步工具，尚不能认定为刚需。**

- Stack Overflow 2026 调查中，编码助手/Agent 已是主要 AI 用途；25.1% 的受访者因输出质量切换工具、10.6% 因组织要求切换。它支持“工具会变，需要保留工作成果”的判断，但没有直接测量对本产品的支付意愿。[原始调查](https://survey.stackoverflow.co/2026/ai)
- LangChain 的 1,340 份问卷中，57.3% 已将 Agent 投入生产、超过四分之三使用多个模型、约 89% 做可观测性。该问卷采集于 2025-11-18 至 12-02，页面发布于 2026；样本偏向 Agent 实践者，不能外推所有企业。[原报告与方法](https://www.langchain.com/state-of-agent-engineering)
- LangGraph 已把 checkpoint、线程恢复、持久状态纳入产品。说明连续性确有需求，也意味着单个运行时的恢复不是空白市场。[官方持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)
- A2A 和 MCP 已有行业协议，应该复用并提供兼容测试。单独发明一份 JSON 格式不会自动成为生态标准。[A2A 1.0](https://a2a-protocol.org/v1.0.0/specification/)、[MCP 版本规则](https://modelcontextprotocol.io/specification/versioning)

竞争判断是基于上述事实的推论：最有机会的切入点是“研发团队跨厂商任务接续 + 权限和审计 + 自托管”，其次是软件厂商嵌入 SDK；普通单 App 的历史同步容易被原厂覆盖。多模型使用也不意味着每个工作流都需要多 Agent 自动编排，后者会增加延迟、Token 和故障点。

## 3. 运营与盈利建议（待验证的假设）

先服务有 2 种以上 Agent、跨设备办公且有交接/审计需求的研发团队。产品承诺应是“带决策、文件、权限与来源的工作接续”，验收标准是目标 Agent 能正确继续真实任务。

| 套餐方向 | 收费价值 | 成本/风险约束 |
|---|---|---|
| Free | 完整的小规模接续体验与分享 | 有限保留时间、容量和出站流量；不承诺无限存储 |
| Pro | 多设备/多 Agent 历史、附件与恢复 | 月费含额度，超额存储/下载明确计价；先验证个人支付意愿 |
| Team（优先） | 工作区、权限、任务交接、审计、统一账单 | 按席位或活跃成员 + 资源额度；避免把每次后台握手都作为用户可见收费项 |
| Enterprise | 私有部署、数据驻留、身份、支持和 SLA | 部署/支持收费；KMS、合规、性能承诺必须有真实验收 |
| SDK/平台 | 将连续性嵌入第三方软件 | 基础平台费 + 已接受事件/存储/流量；不要混淆模型 Token 账单 |

贡献利润 = 实收收入 − 退款 − 渠道费用 − 存储/请求/出站流量 − DB/队列/计算 − 可归因支持成本。当前只有部分收入和用量账本，尚无跨云成本导入与完整毛利报表，因此无法证明“利润最大”。优先同区域部署、lazy download、内容去重、生命周期、租户配额；不要默认跨云复制所有原始附件。

建议先进行 4 周、10–15 个团队的试点，以下是实验门槛而非已达到的指标：每团队至少 5 个真实任务跨 Agent 接续；记录安装耗时、上下文补录耗时、失败原因、W1/W4 留存、活跃团队重复接续、付费转化、净收入与边际成本。只有客户确认任务成功继续的回执才计入 Successfully Continued Tasks；包下载/模型自报成功不算。要求试点实际付费或签采购意向，不用问卷“感兴趣”替代购买证据。

## 4. 架构是否能持续演进

模块化单体 + PostgreSQL 事务边界合理；独立归档 Worker 与 JetStream 已提供局部横向扩展。保持这一结构，先测瓶颈再拆服务。Outbox、Broker、对象存储之间采用至少一次投递和幂等消费，是最终一致性闭环；**不是跨云 XA，也不承诺网络上的 exactly-once**。

下一阶段按证据推进：

1. **商用前**：A2A/MCP 正式版本兼容、严格合同测试；审计/关键非事件计量事务化；支付沙箱与真实结算验收；Marketplace 收款对接或明确禁用付费运营；税务服务接入；真实租户套餐额度执行核查。
2. **可重复交付**：云工作负载身份与凭据轮换、同区域对象存储路由、外部 CSI/RWX 锁验证、真实恢复演练；把 SDK/Agent 版本与操作系统的支持矩阵接入 CI。
3. **增长之后**：归档队列按区域/服务等级分流；按租户压测公平性；为 Event 表分区和历史裁剪设计游标兼容；大型 Continuity Package 改分页/增量，避免一次加载全历史和重建所有快照。
4. **Agent 执行面**：另建可插拔执行适配器，明确任务认领租约、预算、人工审批、取消和补偿；接入 LangGraph 等已有运行时，保留本平台为权威状态层。不要由“有分支和消息”推断“已能自主协调各模型”。

主要扩展边界已有 `storage.Store`、`objectstore.Provider`、`payments.Provider/RefundProvider`、`adaptersdk.Adapter`。当前存储接口较大，后续按模块拆窄接口即可，无需先重写为微服务。数据库串行化热点、全历史载入和 RWX 暂存将先于“Agent 数量”成为容量约束，需要实测。

目前接入目录覆盖 Codex、Claude、CodeBuddy、Cursor、Gemini、OpenCode 的不同接入方式，不代表所有主流 Agent 都已适配。GitHub Copilot、Amazon Q 等仍需要各自官方扩展入口和兼容验收；六语言 SDK 是给宿主软件开发者嵌入的能力，不是绕过 App 沙箱的通用插件安装器。未来若分库分片，需要升级游标/路由协议，不能直接把单库 `server_sequence` 当作跨分片全局顺序。

## 5. 本次实际改动

- 新增公开发现 `/.well-known/agent-continuity.json`、同服务 JSON Schema/OpenAPI 下载，显式声明项目契约、支持的版本与能力边界。
- 修复接续包 Schema 与接口实际字段/空集合编码不一致；用真实 HTTP 响应做 JSON Schema 2020-12 验证。
- 加固全局事件 ID 去重：任务/账号/设备/分支/类型/摘要不匹配时拒绝，不返回其他租户的原事件；增加 HTTP 与 PostgreSQL 回归测试。
- 已接受事件的 `api.mutation` 记录移入 PostgreSQL 同一事务，memory store 同步实现；重放不重复计量，协作者的事件归入任务所有者/组织；HTTP 审计不再生成第二条费用。沿用原费率，不新增收费项，不重写历史账单。
- 四云部署覆盖配置与依赖目录、离线检查、生产配置拒绝用例；修复部署流水线的现场 values 缺失、输入直接进入 shell、canary 重复公开 Ingress、CI Docker context 固定为本机等问题。
- 本地部署增加 Pod 名额与未调度积压检查，避免在共享 Rancher 节点已满时启动升级；不驱逐其他工作负载。
- 修正过度完成声明，增加协议规范与多云运行手册。

本次未对外支付、未向真实云账号创建资源，也没有将公开协议宣称为已有行业认证。详细验收结果见本文末尾和对应本机日志。
